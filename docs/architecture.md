# Архитектура

## Общая схема

```
Источники документов ──► Регистратор ──► Процесс (PostgreSQL) ◄── Раннер выполняет узлы маршрута
 • каталоги (*.pdf)      дедупликация,     RouteKey = тип       • шаг: идемпотентная работа
 • вьюха сторонней БД    повторные прогоны документа            • ожидание: ждёт сигнала
                                                                • сбой → повторы → эскалация
Сканеры сигналов (файлы подписи) ──► будят процессы, ждущие сигнал
```

Три фоновых воркера (`Engine/Workers`): `IntakeWorker` (опрос источников и регистрация), `SignalScanWorker`
(сканеры сигналов), `ProcessRunnerWorker` (единственный исполнитель шагов; также таймауты и досылка писем).

## Основные понятия

* **Маршрут** (`IRoute`) — класс в одном файле: `Step<T>()`, `WaitFor(signal, timeout)`, `Include(fragment)`.
  Ключ маршрута = тип документа (`report`, `zop`).
* **Шаг** (`IStep`) — идемпотентная единица работы. Ошибка = исключение (повторы с backoff),
  `PermanentStepException` = сразу эскалация.
* **Процесс** (`DocumentProcess`) — один прогон обработки документа. Курсор хранится как **id узла**, а не индекс:
  правка маршрута не ломает живые процессы.
* **Статусы:** `Running`, `Waiting`, `NeedsAttention`, `Completed`, `Cancelled`.
* **Валидатор маршрутов** при старте: шаги зарегистрированы, у каждого ожидания есть сканер,
  последний узел — не ожидание.

## Маршруты

| Тип | Шаги |
|---|---|
| `report` | Intake → AutoSign → Verify → MoveToResult → Persist |
| `zop` | Intake → ApplyStamp → SendToSignature → **ждём `{id}.sig`** (7 дней) → Verify → MoveToResult → Persist |

`PersistSignature` (запись подписи во внешнюю БД) — **последний шаг**: после него запись исчезает из вьюхи,
поэтому к этому моменту файлы уже в каталоге результата.

## Регистрация документов

* Уникальность: `(SourceId, ExternalId, Run)`; пока есть активный процесс, повторы из источника игнорируются.
* Запись вернулась во вьюху после `Completed` (в сторонней БД зачистили подпись) = новый `Run`.
  Защита от устаревшего снимка: `CompletedAt < момент начала опроса`.
* `Cancelled` автоматически **не** перезапускается (запись всё ещё во вьюхе); только `POST /processes/{id}/restart`.

## Входные данные документа (`Data`)

Вместе со списком документов источник может отдавать дополнительные данные — например, поля для штампа
(ФИО, даты, номер соглашения):

```
колонки вьюхи → PendingDocument.Data → DocumentRegistration.Data → DocumentProcess.Data → шаг: ctx.Data / ctx.RequireData("...")
```

* `Data` — **снимок на момент регистрации**; для своих промежуточных данных у шагов есть `Bag`.
  Значения — строки (даты — ISO 8601, числа — `InvariantCulture`); преобразуйте колонки так в `IPendingDocumentsReader`.
* Маршрут объявляет обязательные поля: `IRoute.RequiredData` (пример — `ZopRoute`, имена — `DataKeys`).
  Документ с неполными данными **процесс не создаёт**: запись остаётся во вьюхе, в лог один раз пишется предупреждение.
* `ctx.RequireData(key)` в шаге: нет поля = `PermanentStepException`.
* Повторная обработка (`Run` + 1) получает свежий снимок. `restart` после `Cancelled` берёт данные **прежнего прогона**.
* Если данные придётся подгружать отдельным шагом (БД, внешний API) — см. `docs/adding-a-document-type.md`.
* ⚠️ ФИО и подобное — персональные данные: лежат в `processes` и отдаются операторским API.

## Файлы

Рабочие копии: `{WorkingDir}/{processId}.pdf|.orig.pdf|.sig`; на подпись: `{SignatureDir}/{processId}.pdf`, пользователь
кладёт `{processId}.sig`; результат: `{ResultDir}/{processId}.pdf|.sig`. Исходный файл чужой шары не меняется:
`IntakeStep` копирует его, каталоговый источник затем переносит оригинал в `_processed`. Все записи атомарны (`.tmp` + переименование).

## Эскалация

Таймаут ожидания или исчерпанные повторы → статус `NeedsAttention`, письмо (`IEscalationNotifier`), дальше оператор:
`retry` / `continue` / `cancel` / `restart` (см. `docs/operations.md`). Подпись, пришедшую после таймаута, обрабатывает
`retry` на узле ожидания: процесс снова ждёт, сканер сразу находит файл.

## Хранилище: PostgreSQL + EF Core (`DocFlow.Data`)

* Таблицы: `processes` (процесс целиком; `Bag` и `Data` — JSON в `text`, статус — строкой) и `process_events` (аудит).
* **Optimistic lock:** `Version` — токен конкурентности; `SaveAsync` делает `UPDATE ... WHERE "Version" = <ожидаемая>`,
  при расхождении бросает `ConcurrencyException`.
* **Уникальность в БД** (страховка от гонок регистрации): `ux_processes_document_run` — `(SourceId, ExternalId, Run)`;
  `ux_processes_active_document` — частичный индекс: не более одного активного процесса на документ.
  `TryAddAsync` превращает нарушение уникальности (SQLSTATE 23505) в `false`.
* Репозиторий — singleton, на каждую операцию свой короткий `DbContext`; процессы возвращаются без трекинга.
* Раннер берёт готовые процессы пачками по 500 (самые старые первыми).
* Аудит пишется синхронно одной вставкой; сбой записи аудита логируется и не прерывает обработку документа.
* Колонки именуются как свойства (`"Status"`, `"NextAttemptAt"`…); если нужен snake_case — подключите
  `EFCore.NamingConventions` и обновите фильтр частичного индекса в `DocFlowDbContext`.
